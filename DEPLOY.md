**For:** Instinct (build/deploy owner). **Status of this package:** built and
tested locally by loyd; **not deployed**. The live education app and server
are unchanged until the steps below are run.

- **Endpoint (frozen):** `https://mcp.peptidex.ai`
- **Function:** `peptidex-mcp` (Supabase Edge Function, Deno, `verify_jwt = false`),
  running in the shared Supabase project `rggrbtcdqiczadpfvjuv` behind the
  Cloudflare Worker `peptidex-mcp-proxy` — the same pattern as the existing
  education server, and the same deploy route as TrueGift's
  `gift-finder-mcp` (Lovable project → `supabase/functions/<name>/index.ts`
  → publish → read-back verify).
- **Dataset:** `data/library.json`, version **2026-11-18** (served at
  `/health` as `library_version`).

## Source of truth / audit

**This directory (`consumer-portfolio/mcp-prototypes/peptidex-map/`) is the
source of truth for the deployed server.** Nothing deploys from anywhere
else.

- `data/library.json` — the one reviewed dataset (peptides, studies,
  claims, regulatory records, sources, explainers, terms).
- `peptidex_data.py` + `server.py` — the Python mirror (production-shaped;
  the acceptance suite runs against it).
- `edge-function/peptidex-mcp/index.ts` — the Deno source; it imports
  `../../data/library.json`, so the dataset has a single home.
- `edge-function/dist/index.ts` — the **self-contained deployable**,
  generated by `edge-function/build.py` (dataset inlined). This is the file
  that gets deployed, and the file the deployed function must match.
- Audit rule (TrueGift precedent): after every deploy, **read back the
  deployed function source and compare it with `edge-function/dist/index.ts`**
  (byte-identical except, at most, a trailing blank line), and confirm
  `GET /health` reports the expected `library_version`. Record the deploy
  (date, dataset version, read-back result) in `BUILD-STATUS.md`.
- Editorial changes land here first, with the test suite green, before any
  redeploy. Candidate sources are never edited into the dataset without
  review — the dataset is the approved snapshot, per build spec v0.2 §4.

## Pre-deploy gates

1. `tests/test_peptidex_map.py` — **all tests pass** (34/34 at package
   build; see `BUILD-STATUS.md` for the run record and the exact command).
2. `deno check` clean on `edge-function/peptidex-mcp/index.ts` and on the
   generated `edge-function/dist/index.ts`.
3. Regulatory freshness: no regulatory record may be past its
   `next_review_due` at deploy time (current records: checked 2026-11-17,
   due **2026-11-24**). If the date has passed, the records must be
   rechecked against their primary sources and the dataset version bumped
   first — the server withdraws stale status conclusions automatically,
   but a release should not ship already-stale records.
4. Submission gates outside this package stay as they are: the truthful
   privacy policy and Howard's attestation answers are Instinct/Howard
   items (build spec v0.2 §7). **Do not submit until those clear.** This
   deploy changes the server only; it is not a submission.

## Deploy steps

1. From this directory, regenerate the deployable:
   `python3 edge-function/build.py` → `edge-function/dist/index.ts`.
2. In the PeptideX Lovable project (`peptidex`,
   `f4cb8a8a-633a-47b4-9c50-93e1ecb60f80`), replace
   `supabase/functions/peptidex-mcp/index.ts` with the contents of
   `edge-function/dist/index.ts`, verbatim (Lovable edit, the TrueGift
   route). Confirm the function targets the shared project
   `rggrbtcdqiczadpfvjuv` and `verify_jwt = false`.
3. Confirm the function secret `OPENAI_APPS_CHALLENGE_TOKEN` is still set
   to the **current binding** (unchanged from the education app — do not
   rotate it as part of this deploy). The challenge route 404s when unset.
4. Publish/deploy the Lovable project.
5. Read back the deployed function; compare with `dist/index.ts` (audit
   rule above).
6. Verify live, from outside:
   - `GET https://mcp.peptidex.ai/health` → `{"status":"ok", "service":
     "peptidex-reference-map", "library_version":"2026-11-18"}` (or the
     newer version being deployed).
   - MCP `initialize` + `tools/list` → exactly the nine read-only tools.
   - Spot-call `search_peptides` ("Bepecin" → BPC-157),
     `get_peptide_card` (tb_500), `get_regulatory_record` (bpc_157, US),
     and one refusal (a dosing-shaped search query → rejected, no echo).
   - `GET https://mcp.peptidex.ai/.well-known/openai-apps-challenge` →
     the current binding token.
7. Run the in-ChatGPT Developer Mode set (spec 08 §9 positives/negatives,
   adapted to the map operations) before any submission step.

## Rollback

The server is stateless and stores nothing, so rollback is a pure
redeploy — no data migration, no user impact:

1. Take the previous release's `edge-function/dist/index.ts` (each release
   is kept with its `data/library.json` snapshot in version control here).
2. Repeat deploy steps 2–5 with that file.
3. Verify `/health` reports the **previous** `library_version` and repeat
   the spot-calls.
4. Record the rollback in `BUILD-STATUS.md` (date, from/to versions, why).

**Withdrawal control** (build spec v0.2 §5): to pull a single card or
record urgently, remove it from `data/library.json`, bump
`meta.dataset_version`, regenerate, redeploy, verify. The catalog then
fails clearly for that ID instead of serving withdrawn content.

## Versioning

- `meta.dataset_version` in `data/library.json` = the library version;
  bump on every content change; it is what `/health` reports.
- Per-peptide `card_version` and `last_review_date` / `next_review_due`
  ride inside the dataset; regulatory records carry their own
  `date_checked` / `next_review_due` (weekly recheck cadence).

## Analytics — untouched by this deploy

This package and its deploy touch **only** the `peptidex-mcp` function.
peptidex.ai site code is not modified, and all existing site analytics
stay exactly as they are: Google Analytics (G-BFLE721HPV), Beehiiv,
referral tracking, and Lovable analytics. The MCP server itself collects
no analytics and no user data: no accounts, no input logging, nothing
stored (the serving code contains no logging calls — covered by a unit
test in the suite).

## Future clinical-service seam (design only — nothing built)

Build spec v0.2 §6 defines a possible later clinical/pharmacy service.
This package deliberately leaves a clean seam and builds **none** of it:

- The reference app is a bounded, read-only, no-PHI service with a fixed
  dataset. It contains **no dormant clinical operations** — the tool list
  is exactly the nine read-only operations, verified by the test suite.
- A future clinical service would be a **separate service on
  peptidex.ai's side**, with its own authentication, its own data store,
  its own access controls, audit trail, and retention/deletion policy,
  and its own security review. It must not share this app's credentials,
  tables, or function, and **no patient data ever flows back into the
  reference app or its dataset**.
- The only permitted interface is one-way and identifier-level: the
  clinical service may reference this catalog's stable peptide IDs. It
  may not write to `data/library.json`, and this app exposes no write
  path of any kind.
- Activation requires healthcare counsel's assessment and a fresh
  platform policy assessment first (spec v0.2 §6) — an API contract or a
  vendor is not a license. Until then, the seam is documentation only.
